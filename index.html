Documentation / Introduction

Agent-0

An agentic coding runtime built around the limits of small open-weight models. Many small specialists, tight context, hard guardrails.

Agent-0 is a coding runtime for small and medium open-weight models. It combines specialist agents, targeted code context, visible model routing, and approval-gated tools to handle multi-step software tasks under the Takneek constraints.

Problem statement

Small models can be inexpensive and capable, but they are less reliable when one model must plan, edit, test, and recover from failure in a large context. Agent-0 splits these responsibilities, limits the context supplied to each stage, and keeps the user in control of changes.

Key features

Multi-agent orchestration

Fixed 5-stage coding pipeline (Planner → Retriever → Coder → Verifier → Reviewer) plus a registry-driven multi-agent path for everything else. Both share the same tool registry and approval boundary.

Smart provider routing

Chooses a configured model and provider using context fit, availability, cooldown, and cost. Route decisions are shown to the user, and retryable failures fall back without losing progress.

Automatic context compaction

Reduces history before a model reaches its context limit while retaining the objective, completed work, failures, changed files, and project rules.

Semantic code retrieval

Finds relevant files, symbols, and compact code slices so agents get useful context rather than the full repository.

Long-horizon resume

Completed stages are checkpointed so interrupted tasks can resume without repeating finished work.

Manual context + /bytheway

Pin files or line ranges to the task. /bytheway handles side questions in an isolated call, keeping the main task focused.

Autonomous tools + HITL

Agents can inspect the workspace and run approved actions. File changes are previewed as diffs and can be accepted or rejected hunk by hunk.

AGENTS.md project rules

Root AGENTS.md instructions are loaded into the workflow and retained when context is compacted.

Persisted trace spans

Task events record stages, routing, approvals, and failures so work can be inspected and resumed.

System overview

Three layers, one boundary. HeadlessRuntimeService is the application boundary; every client goes through it, and no orchestration lives in the clients themselves.

Data flow

A coding task moves through the system as follows:

  1. The client (TUI in-process, or Browser/Desktop via Loopback GUI server POST /api/task + SSE) posts a user prompt to HeadlessRuntimeService.executeTask() / resumeTask({taskId}).
  2. The runtime resolves the caller's agent (isSelectableAgent: only Architect/Coder + .agentic/agents/*.md), checks the routing heuristics, and picks one of four paths plus the focused specialization: verification-only → Verifier; coding pipeline (Planner→Retriever→Coder→Verifier→Reviewer, with Planner-driven 1→2-4 subtask rewrite); Architect read-only (tools + context, no mutation); Chat (no tools, no system prompt, no context) — plus focused single-file implement/add @path with preloaded hash, 2-turn Coder cap, 3-turn Verifier, no rollback.
  3. The chosen orchestrator runs its stages sequentially (parallel read-only later). Each stage builds a scoped request — Planner read-only, Retriever deterministic not LLM (up to 10 × 40-line slices), Coder per-subtask slice — and hands it to AgentRunner. Verifier must end with exact VERIFICATION_PASSED on its own line and only counts with real tool evidence; Reviewer is read-only and deterministic for bounded single-file work.
  4. Inside the runner, request size is estimated (~4 chars/token, reserve 1024), compaction may fire (trigger 75% → 60%, after error →45%, keep ≥2 exchanges, ≤4 passes, ≤2 recoveries, fallback 8k, via prune_ast), the provider gateway picks a route by eligibility (tool support, context fit, stage minimum window floor, cooldown) then bias (capacity=largest params, economy=cheapest, balanced=operator order; unknown params=0), and the model responds with text and any tool calls.
  5. Tool arguments are validated by Ajv before preview, previews are prepared with stable base-hash hunks, approval is requested for side-effect tools (fail-safe default ask), hidden handoff_agent proxies enforce allowedTools+delegatesTo, and approved calls are executed. Results are returned to the model as structured tool messages with matching call IDs; duplicate tool-call cache (4× identical → skip) and failure fingerprints guard loops.
  6. Every state transition is written to the databases — global global.db (settings/credentials/baseUrls/modelIds/validation), per-project projects/<projectId>/project.db (sessions/transcripts/tasks/state/events/context/checkpoints/recovery/traces/agent definitions incl. project .agentic/agents), and per-project retrieval.db (or .agentic/data/retrieval.db standalone) with FlatCPG WAL; all in SQLite WAL journal mode.
  7. The runtime emits and persists events (route with reason/contextTokens/cost/failure class, tool cards, approval requests, stage transitions, compaction) and streams them over SSE via RuntimeTransport to the workbench/TUI route pane.

Persistence

Three SQLite databases, each with a specific job:

  • Global database (global.db in %LOCALAPPDATA%\agentic-runtime or $XDG_DATA_HOME/agentic-runtime). Settings, provider credentials (plaintext, keychain follow-up), provider base URLs and model IDs, last provider validation result. Agent definitions no longer live here — moved to project DB for isolation (global agents table dropped on first open).
  • Project database (one per canonical project root, projects/<projectId>/project.db where projectId=SHA256(realpath).slice(0,32)). Sessions and transcripts, tasks and serialized task state, runtime events, manual and generated context items, orchestration checkpoints with plan expansions, recovery state, trace spans (trace_spans), and agent definitions including any the project ships itself.
  • Retrieval database (one per project, projects/<projectId>/retrieval.db when composed, or .agentic/data/retrieval.db standalone). File hashes and metadata, symbols with line spans, and the definition/reference/call/import/export edge graph plus FlatCPG persisted via Rust Wal (bincode, 8-byte LE len, memmap2).

SQLite databases run in WAL journal mode — readers see a stable snapshot from the main file while writers append to the WAL, so the TUI can read task state while the runtime writes checkpoints. Rust FlatCPG uses a separate memory-mapped Wal. Isolation is by file-per-project plus projectId filter on every project-scoped query; two projects sharing a database path in tests (file + filter) still cannot see each other's data, covering files/symbols/edges, sessions/tasks/traces, agents/rules, and filesystem root.

Security & isolation

  • Workspace sandboxing. All file paths are resolved against a single canonical workspace root. Paths outside the root and symlink traversal are rejected. Reads are UTF-8 only and bounded by size; writes are atomic and conflict-checked.
  • Network policy. Web tools accept only HTTP and HTTPS, reject private and reserved network targets, do not execute page scripts, cap response size at 2 MB, and bound crawls to 25 pages on the same domain.
  • Shell policy. Commands receive a restricted environment, run under a timeout with bounded output, and inherit the runtime's abort signal. Windows uses cmd.exe; Linux and macOS use /bin/sh.
  • Approval boundary. Every side-effect tool is approval-gated; the runtime cannot mutate files, run shell commands, or push to Git without explicit user consent.
  • Trace redaction. Secrets and sensitive field names are stripped before trace persistence.

Known limitation. Provider credentials are stored plaintext in the global SQLite; the database file is the current secret boundary. Moving credentials to OS keychain-backed storage is a documented follow-up.

Trade-offs

The architecture reflects a set of deliberate choices, each of which had a plausible alternative:

ChoiceAlternative consideredReasoning
TypeScript orchestration with a small Rust sidecar Full Rust runtime, or pure TypeScript TypeScript iterates faster across providers, tools, and persistence. Rust wins on tree-sitter and signature pruning where a native library is materially cheaper. Process isolation keeps native parser crashes out of the runtime.
Sequential 5-stage pipeline Parallel-agent scheduler Multiple agents mutating one working tree in parallel are hard to recover safely. Sequential stages checkpoint cleanly. The cost is latency on independent work.
TypeScript compiler API plus edge-graph retrieval Vector-DB embeddings, or a full code-property graph Embeddings alone miss structural cross-file relationships. A full CPG is expensive to populate incrementally. The compiler-API path is deterministic, cheap, and gives real caller/callee signals.
Base-hash-bound line hunks for HITL Structural AST merge Line hunks are language-neutral, testable, and fail closed on a stale base. They support partial approval today.
Three SQLite databases Postgres or a custom store SQLite installs nowhere, inspects with any tool, and gives clean transactional boundaries per scope. Credentials sit plaintext; schema evolution is manual.
Same-model compaction Dedicated summarization model A separate summarizer adds a round-trip cost and latency. Structured extraction is heuristic, not free-form summarization.
Structured JSON tool-calling format with Ajv validation Free-form string prompting or uncontrolled text parsing Tool-calling format used: Small open-weight models produce more reliable output on narrow, explicit tool surfaces. By enforcing a strict JSON Schema for tool calls and validating arguments via Ajv before the user sees an approval prompt, we prevent hallucinated arguments and ensure execution safety.

Setup & installation

Requirements

  • Node.js 22.5.0 or newer (uses built-in node:sqlite; verified with 24)
  • pnpm 9.15.5 pinned (corepack enable && corepack prepare pnpm@9.15.5 --activate; npm/yarn will not resolve workspaces)
  • Rust ≥1.85.0 (crate uses edition = "2024"; required to build, optional at runtime — missing sidecar degrades to regex/tool error)
  • Git (for clone + git_* tools) and ripgrep (rg) for search; or set AGENTIC_RIPGREP_PATH
  • Optional: Ollama for zero-cost local inference
  • Recommended: 16 GB RAM and 8 GB VRAM for the local model tier

Agentic pipeline

Two orchestrators coexist in the runtime. TaskOrchestrator runs the fixed five-stage coding pipeline. MultiAgentOrchestrator runs registry-driven agents through AgentRunner, supports bounded handoffs, and is the general execution boundary for everything that isn't a mutation-oriented coding request.

flowchart TD Prompt[Persisted user task] --> Eligible{Built-in Architect or Coder?} Eligible -->|No| Direct[Direct registry-driven path] Eligible -->|Yes| VerifyOnly{Read-only verification request?} VerifyOnly -->|Yes| Verifier[Direct Verifier path] VerifyOnly -->|No| Work{Workspace work requested?} Work -->|Yes| Pipeline[Coding pipeline 1.Planner→2.Retriever→3.Coder→4.Verifier→5.Reviewer] Work -->|No| About{Refers to opened project?} About -->|Yes| Architect[Architect: read-only tools + context] About -->|No| Chat[Chat: no tools, no system prompt] Verifier --> Finish[Persist transcript, task state, events, traces] Pipeline --> Finish Direct --> Finish Architect --> Finish Chat --> Finish

Focused specialization: implement/add @path with single @file preloads hash, 2-turn Coder (no read_file), 3-turn Verifier, no rollback.

Task routing

Routing lives in HeadlessRuntimeService.executeTask() and applies in this precedence (automatic; Architect is entry point, user never classifies; only Architect/Coder + .agentic/agents/*.md are selectable via isSelectableAgent):

  1. Verification-only routing. If the selected agent is built-in Architect or Coder, and the request asks to run, execute, rerun, check, or verify tests, a suite, a build, lint, type checking, syntax checking, or format checking — and the request either explicitly forbids mutation or does not contain a mutation keyword — the runtime routes straight to the Verifier with verifier-scoped tools. Handoffs and workflow continuation disabled. Prevents “run the tests” from triggering the full pipeline. Example: “Run the tests without modifying files.”
  2. Coding-pipeline routing. After verification-only is ruled out, prompts from built-in Architect/Coder enter the fixed pipeline when requestsWorkspaceWork is true — requires an artifact request, a workspace reference, or a bare action verb, and returns false outright for anything shaped as a question. Keywords include add, build, change, create, debug, delete, edit, fix, implement, migrate, modify, patch, refactor, remove, rename, test, update, write. This is a regex heuristic, not semantic — ambiguous prompts can still take the wrong path, and custom agents never enter the pipeline even with those keywords.
  3. Direct registry-driven routing. Everything else — conversation, research, read-only questions not matching verification, custom agents, requests not matching coding heuristic — goes to MultiAgentOrchestrator (registry-driven). Two sub-paths: if the prompt refers to the opened project → Architect (read-only tools + session context, no mutation); otherwise → Chat (tool-free, no system prompt, no context). Handoffs to other enabled agents allowed subject to depth/count/budget/cancellation. “What is a closure” → Chat; “What files are in this repo” → Architect (workspace reference separates them).

The five stages

Fixed shape, not fixed length. The static plan carries one placeholder code step; the Planner may replace it with 2–4 subtasks.

1. Planner. LLM with read-only tools, using built-in general (Architect) definition. Receives objective, prior session history, project context, and earlier stage results. Emits a small testable plan. May end with a fenced subtasks block — orchestrator replaces the placeholder with one code-N step per subtask (bounded at 4, “do not split one-file work”), first inherits retrieval dep, Verifier now depends on last. Degrades to single generic step on missing/malformed/single-entry/no-prompt; survives restart via orchestration state replay; emits plan_expanded event / plan_expansion trace.

2. Retriever. Deterministic — not an LLM call and does not use the registered Retriever agent definition. Queries the semantic retrieval index with the objective and the Planner output, returns up to ten compact slices at forty lines each (compact file+line slices, not whole files).

3. Coder. One call per coding step — each sees only its own slice of the objective plus the shared retrieval evidence. Receives objective, current project + manual context, Planner output, retrieval slices, and prior stage summaries. Has workspace-mutation tools, read-only Git inspection, shell tools, semantic retrieval, and Rust analysis tools. Mutations and shell-backed calls pass through approval.

4. Verifier. Runs syntax and compile checks, runs relevant tests, inspects the Git diff (receives the list of files the run actually produced), reports exact commands and failures. Must end with exact VERIFICATION_PASSED on its own line — markdown decoration/trailing checklist does not fail a pass, prose mention does not pass — and counts as evidence only if a real verification tool actually executed (prevents hallucinated js_verify/py_verify success). Receives root AGENTS.md so it enforces project rules even under compaction.

5. Reviewer. Receives the plan, retrieval evidence, implementation result, and verification result. Read-only. Produces the final user-facing summary. Cannot run commands or modify files. For bounded single-file work it completes deterministically instead of paying for a second model call.

Execution is intentionally sequential (parallel read-only later). Every stage is checkpointed to project SQLite before and after; resumeTask({taskId}) reloads the checkpoint and skips completed stages. The static plan + expansions and failure fingerprints survive resume; focused single-file edits skip the general recovery graph.

Recovery

When the Verifier reports failure, the recovery state machine takes over (not a failed task):

  1. Check the mutation journal for unsafe external side effects — approved workspace file mutations are reversible; shell, Git, network, package-manager, or other external-process effects are not. If any are present, automatic recovery stops and the failure is surfaced (do not guess).
  2. Otherwise, roll back file mutations in reverse order with preserveCreatedFiles — edits to pre-existing files are reverted, newly created artifacts are kept for the corrective pass to overwrite (early bug deleted the only copy). Each rollback re-verifies the pre-image hash; if the current file hash doesn't match, the user edited it and their content is preserved — stop replanning.
  3. Refresh the semantic index for the changed files (stat→hash→re-extract, 750ms→131ms warm).
  4. Ask the Planner for a materially different plan — not a blind retry — with verifier evidence attached.
  5. Retrieve fresh context for the revised plan.
  6. The Coder applies a freshly approved correction.
  7. The Verifier runs again.

The workspace service holds real mutation pre-images and hash-guarded rollback primitives. Note that in the current build the default file tools do not yet forward their workspaceMutation records to the runtime journal — a Priority-0 wiring gap tracked in the implementation-status document — so end-to-end hash-guarded rollback is not complete. A focused single-file verifier failure also does not launch this graph; it reports the written artifact intact.

Loop safety

Twelve independent limits at four scopes (not round numbers — set against the $0.50 ×10 accuracy / time-cost scoring formula, below the 2700s/$0.50 hard ceilings):

  • Duplicate tool-call cache. AgentRunner caches tool calls by name, arguments, and workspace revision; identical call against unchanged workspace reuses a concise skip. After four identical duplicates, the run stops with a visible safety message.
  • Merkle state tree. Rust StateTree (BLAKE3) hashes each post-mutation workspace state into a rolling 10-state history, task-namespaced; a run that edits→reverts→re-edits succeeds per-step but repeats a prior workspace state and stops as non-retryable — complements failure fingerprints.
  • Failure fingerprints. Identical failure twice stops the step; repeated failure signatures in the same task stop the loop.
  • Step and request budgets. 2 attempts per stage (1 when focused), 10 stage attempts total, 48 model requests per task, 192 tool calls per multi-agent run, $0.50 real provider spend per task, 30 minutes per runtime execution/resume invocation (wall clock restarts fresh; spend and model-request count survive resume).
  • Handoff budgets. Depth 4, 8 handoffs total, 2 per agent pair, duplicate active-handoff detection, shared model-request and duration budgets.

Provider routing & failover

The gateway ranks configured routes for each request in two layers. Eligibility is absolute first:

  1. Tool support (if the stage requires tools)
  2. Estimated context fit against the model's window (request + reserved output)
  3. Stage-specific minimum window floor — a preference, not a hard constraint (if nothing clears it, ranking repeats without it)
  4. Cooldown state (recently failed routes are demoted)

Order among eligible routes is then decided by the request's bias:

BiasFirst sort keyUsed for
balancedoperator preference orderordinary coding work (default)
capacitylargest known total parameter countplanning a complex task, verification, review
economylowest estimated costretrieval summarisation, chat, trivial requests

Remaining ties fall through preference → estimated cost → context-window size → stable provider/model ordering. A bias only reorders eligible routes, never promotes an ineligible one; capacity treats unknown parameter counts as 0. Task complexity is classified syntactically (prompt length, concrete file refs, conjunctions, multi-step vocab) — simple is narrow; anything pointing at concrete code stays on the operator's order.

Retryable failures place the failing route on cooldown and trigger a failover to the next ranked route without rebuilding the request (same message/tool state, costs latency not progress): rate limits (HTTP 429) / transient 5xx / timeouts / connection errors / context-length errors → 2 min cooldown; quota/billing exhaustion incl. HTTP 402 → 30 min cooldown and continue fallback. Authentication and invalid-request failures are terminal (do not hide behind fallback). Judgment stages (Verifier/Reviewer) briefly wait for a preferred hosted route before falling back to the excluded local route as last resort.

Every routing decision emits an event with provider, model, attempt number, human-readable reason, estimated context tokens, estimated cost when available, and failure classification. The TUI renders this activity in a route pane.

Context compaction

Compaction is deterministic — it never calls a model (costly when context is largest and risks hallucination). It runs inside AgentRunner before every model request and again after a provider returns a context-length error. Defaults:

  • Trigger at 75% of the model's usable window
  • Compact toward 60% on the normal threshold path
  • Compact toward 45% after a context-limit error (aggressive recovery)
  • Keep at least two recent exchanges; the most recent exchanges and the last user message are never folded; project rules survive every compaction
  • Up to four compaction passes per turn
  • Up to two context-limit recovery attempts (re-enter with tighter target)
  • Fallback window of 8,192 tokens when the model declares no window
  • Reserve 1,024 output tokens by default; ~4 chars/token estimate

Each pass runs six steps:

  1. Find read_file tool results in history.
  2. Ask the Rust sidecar to prune those source files to signatures via prune_ast (supported extensions only; unsupported returns original).
  3. Group assistant tool calls with their corresponding tool results.
  4. Select older exchanges to remove while keeping recent and current user exchanges intact.
  5. Build a structured CompactedTaskState (fields, not prose) and replace the removed history with a single compaction system message. Successive compactions merge into the existing state rather than summarising a summary.
  6. Repeat if the request still exceeds the target; stop folding if a pass did not shrink the request.

The structured state preserves — in bounded form — the current objective, plans (including plan expansions), completed work, failures and rejected hunks, changed files and their hashes, verification status, retrieved slices with reasons, project rules from AGENTS.md, and open questions. Compaction checkpoints are emitted as events and stored as task context/state, so a restart or resume sees the compacted view too.

Semantic retrieval

The retrieval database contains:

  • Project records (keyed by canonical projectId=SHA-256(realpath))
  • File hashes and metadata
  • Symbols and their line spans (real multi-line spans for tree-sitter)
  • Definition, reference, call, import, and export edges plus FlatCPG graph edges

Extraction runs in three tiers, strongest first:

TierLanguagesProduces
typescriptTS, TSX, JS, JSX, MJS, CJSBindings-resolved symbols, imports/exports, references, calls, relative module edges, compact signatures (compiler API)
tree-sitter (Rust sidecar)Python, Go, Rust, C, C++Parsed symbols, multi-line spans, attributed calls with visibility rules (pub/capital/static/_), real spans
ripgrep-texteverything elseRegex declaration and import lines + path/text fallback

Missing or failing sidecar degrades that tier to the regex fallback. Ripgrep supplies path and text fallback across all languages.

Incremental indexing is stat→hash→re-extract, cheapest first: stat (size+mtime) without reading; if changed, read+hash; if hash differs, re-extract transactionally. Agent writes move mtime so are never missed. Generated, dependency, database, archive, binary, and common build directories are ignored at discovery (no positive glob in wildcard case, otherwise ignores would be disabled by ripgrep's override).

Ranking

Ranking blends eight signals: exact symbol match, partial symbol match, exported-definition weight, edge weight across the five edge kinds (definition/call/import/export/reference), file-path match, ripgrep text match, one-hop graph neighbors, and recent file modification — plus personalised PageRank (restart 0.15, 10 iters, ordered by descending mass, ties by index) over FlatCPG. Bands are explicit: exact 120, exported 88, ordinary 76, graph-only 64–75, text 52; a named symbol always outranks a graph-only hit. Results come back as compact file+line slices with file, lines, and reason; the API does not normally return whole files; overlapping spans merged and capped at 2 per file.

Poor-result recovery

If the exact query returns zero candidates, retrieval splits the query into identifier terms and prompt terms and retries (marked broadened). If a query produces excessive candidates, results are ranked and capped at 2 per file (marked narrowed). If nothing survives, the response says so rather than returning noise. The response records whether retrieval was broadened, narrowed, or remained empty, and slices carry their reason so the Planner/dashboard can revise and show why each chunk was included.

Approval policy

The runtime uses a fail-safe policy: read-only workspace, search, retrieval, Rust-analysis, and Git-inspection tools run automatically; web tools (web_search, browse_url, crawl_site) and every other tool require approval even though they are read-adjacent — conservative network policy. New tools require approval unless they explicitly declare approval: "auto" in their core tool definition; a missing approval defaults to ask (AgentRunner fail-safe).

Tool arguments are validated by Ajv against the tool's JSON Schema before preview or approval — a hallucinated call is rejected with a readable error the model can act on rather than being executed. Successful mutation-tool calls by the Coder are recorded as untracked external side effects when they touch state the runtime cannot reverse (Git pushes, package installs, arbitrary shell state). Presence of such a record blocks automatic rollback, since guessing at reversal would be worse than surfacing the failure.

HITL diff review

Before a file mutation, WorkspaceFileService produces a diff preview containing:

  • Workspace-relative path
  • Base SHA-256 hash of the current file contents (or null for a new file via create_file)
  • Proposed hash after the change
  • Unified text diff
  • Stable line-hunk IDs (h1:${hash(identity)} with version:1; path + line range + content hashes)
  • Original and replacement text for each hunk
  • Optional warnings (e.g., This change removes previously defined: add, subtract when a full-file rewrite would drop exported symbols)

Approval can be boolean (true=accept all, false=deny) or structured (acceptedHunkIds/rejectedHunkIds); rejected hunks are returned into model context so the Coder works around them instead of retrying the same patch. For delete_file, a fully accepted preview deletes the file rather than applying hunks. The TUI supports per-hunk navigation, toggle accept/reject, apply selected, accept-all, and reject-all. Before applying:

  1. Re-read the file.
  2. Verify the base hash still matches (stale file fails closed).
  3. Rebuild the proposal and verify the approved preview still matches (proposedHash + hunks JSON equality).
  4. Validate hunk IDs: reject duplicate acceptedHunkIds, unknown IDs, and overlapping hunks (sorted reverse by startLine); verify original slice still matches file content.
  5. Apply accepted, non-overlapping hunks in reverse order.
  6. Write atomically.
  7. Return rejected hunks to the model context so the Coder can continue around them.

A partial approval never silently applies rejected content; a base-hash mismatch never overwrites a user's concurrent edit. A stale preview or content mismatch throws before any write.

Long-horizon resume

Pipeline stages checkpoint before and after each stage. Stage attempts and failure fingerprints are persisted; plan expansions (code-1…code-4 from Planner subtasks) are persisted and replayed on resume; the task-wide model-request count and real provider spend ($0.50 budget) are persisted; pending recovery state is persisted. Paused model work restarts from the durable stage boundary.

To resume programmatically:

typescript
const runtime = await createHeadlessRuntime(config);
const result  = await runtime.resumeTask({ taskId });  // ResumeTaskInput {taskId, agentId?}

resumeTask() reloads the checkpoint and skips already-completed stages. The 30-minute wall-clock window (not 10) starts fresh on each invocation; the per-task model-request (48) and spend ($0.50) budgets survive resume so a task cannot escape its caps by being restarted. Note: an arbitrary shell process, an in-flight provider HTTP request, or an exact mid-tool state is not resumable in place — resume happens from the nearest durable stage boundary.

Trace data

The trace_spans table stores:

  • Project, session, task, trace (traceId == taskId), and span IDs, plus parent span ID
  • Span kind and name (task, pipeline_step, plan_expansion, agent, model_call, tool, provider_attempt, compaction, isolated_question), status, separate error text
  • Serialized input and output (separate usage_json vs cost)
  • Context artifacts
  • Usage and cost
  • Start, end, and duration
  • Provider, model, agent, stage, and tool identifiers

Secrets and sensitive field names are redacted before persistence (upstream runtime, not DB layer). Query the current hierarchy with:

typescript
const spans = await runtime.listTraceSpans(taskId);  // SessionStore.listTraceSpans(traceId) where traceId==taskId

Spans are currently created for tasks, pipeline stages, agents, provider attempts, context compaction, and isolated questions; routing, task, pipeline, approval, agent, and tool events are also stored in the project event log. Known incompleteness: AgentRunner does not yet populate correlation fields (model_request lacks callId/complete request, model_response lacks matching callId, tool_requested/tool_completed lack spanId/parentSpanId, toToolMessage() does not copy contextArtifacts) — so model-call and tool spans are not created through the intended path, provider-attempt spans attach above the missing level, and per-model usage is not reliably captured. The headless runtime has listTraceSpans(taskId) and the IDE dashboard can display traces, but rendering a full correlated hierarchy remains follow-up work.
